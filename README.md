# 메뉴 관리 — 서버를 바꿔 다시 만드는 바이브 디자인

이 저장소는 **참고용 완성본**이다. 실습은 각자 로컬에서 진행하고, 막히거나 다 만든 뒤에 비교용으로 열어 본다.

```
spring-test/
├─ chap06-spring-data-jpa/   springdoc 까지 적용된 서버
├─ api-docs.json             2-2 에서 뽑는 명세. 결과물 예시
├─ AGENTS.md                 4장에서 쓰는 지침 파일
└─ menu-app/                 5장에서 만드는 React 앱
   ├─ design/montage.tokens.json
   ├─ scripts/build-tokens.mjs
   └─ src/
```

---

## 1. 개요

### 1-1. 변경점

디자인은 그대로다. **서버와 통신하는 방법만 달라진다.**

|           | PokeAPI                           | chap06                                                   |
| --------- | --------------------------------- | -------------------------------------------------------- |
| 명세      | 공개 문서 페이지                  | **API 명세 문서를 직접 만든다**                    |
| 응답      | 원시 JSON                         | **정상 응답 템플릿과 오류 응답 템플릿이 존재한다** |
| 다음 자원 | 응답이`url` 을 준다             | **설계 자체에 없는 내용이다**                      |
| 목록      | 이름과 url 뿐 → 마리당 추가 요청 | **DTO 가 완전하다**                                |
| 페이징    | `offset` 을 직접 계산           | `Pageable`인터페이스로 구현. **1부터** 센다      |
| 쓰기      | 없다                              | **등록/수정/삭제가 있다**                          |
| 서버      | 이미 떠 있다                      | **직접 실행한다 (`localhost:8080`)**             |

### 1-2. 사전 준비

- **MySQL** 이 실행중일 것. 포트 `3306`
- **Node.js 20.19 이상 또는 22.12 이상**. `node -v`
- **`chap06-spring-data-jpa` 원본.**
- 원티드 디자인 시스템인 `montage-web-main` 과 추출한 디자인 토큰 `montage.tokens.json` 을 재사용.

실습을 진행할 작업 폴더를 하나 정해 두고 시작한다. 폴더명은 자유롭게 만들어도 된다.

```
menu-test/
├─ montage-web-main/           4일차에 받은 것. 읽기만 한다
└─ chap06-spring-data-jpa/     원본을 복사해 온 것
```

## 2. 백엔드 준비

### 2-1. 서버 실행

`sql/` 의 두 파일을 순서대로 실행한다. 계정과 데이터베이스를 만들고 표와 데이터를 넣는다.

```
sql/00_01_CREATE_USER_DATABASE.sql
sql/00_02_DB_SCRIPT.sql
```

`src/main/resources/application.yaml` 의 접속 정보가 맞는지 확인한다.

```yaml
url: jdbc:mysql://localhost:3306/menudb
username: ohgiraffers
password: ohgiraffers
```

IntelliJ에서 SpringBoot 앱을 실행한다.

```bash
./gradlew bootRun
```

브라우저에서 아래 주소로 요청했을 때 JSON 응답을 해주면 서버는 정상 실행중이다.

```
http://localhost:8080/api/menus
```

**확인**

- 응답이 `{ "httpStatus": 200, "message": ..., "result": { "menus": [...] } }` 모양인가
- `config/CorsConfig.java` 가 `http://localhost:5173` 을 허용하고 있는가.
  React 앱이 5174 로 뜨면 요청이 막힌다. 그때는 먼저 뜬 앱을 끄고 5173 으로 다시 띄운다

### 2-2. API 명세 추출

> 이번 실습의 키포인트로, PokeAPI같이 다른 서비스의 API 명세를 참조하는 것이 아니라 내가 개발한 REST API 서버의 API 명세를 직접 준비한다.

**① API 문서화(Swagger UI)를 위한 의존성을 `build.gradle`에 추가.**

```gradle
implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:3.1.0'
```

`application.yaml` 에 경로를 적는다.

```yaml
springdoc:
  api-docs:
    path: /v3/api-docs
  swagger-ui:
    path: /swagger-ui.html
    display-request-duration: true
    operations-sorter: method
```

**② Spring Boot를 다시 실행하고 `http://localhost:8080/swagger-ui.html` 에 접속이 되는지 확인한다.**

엔드포인트 경로와 HTTP 메서드는 잡히지만 **설명이 비어있을 것이다.**

**③ 어노테이션을 붙인다.**

AI 에이전트에게 아래와 같이 프롬프트를 입력한다.

```
컨트롤러에 OpenAPI 어노테이션을 붙여줘. @Tag, @Operation, @ApiResponses, @Parameter 를 사용해줘.

- 이 프로젝트의 정상 응답은 ResponseMessage 템플릿이고 실제 데이터는 result 안에 있다.
  result 안에 무엇이 어떤 이름으로 담기는지를 @Operation 의 description 에 적는다.
- 페이지 번호가 1부터인 것, 상태 코드가 언제 무엇인지도 함께 적는다.
- 컨트롤러의 동작은 바꾸지 마.
```

마지막 줄을 넣지 않으면 어노테이션을 추가하면서 자칫 기존 코드를 수정할 수도 있다.

**④ 명세를 파일로 저장한다.** `http://localhost:8080/v3/api-docs` 의 내용을 그대로 저장한다.

```
menu-test/api-docs.json
```

**확인**

- Swagger UI 에 메뉴 8개, 카테고리 2개가 보이는가.
- 각 API 를 펼쳤을 때 **`result` 안의 키 이름이 설명에 적혀 있는가.**
  `result` 는 `Map` 이라 명세에 내부가 자동으로 드러나지 않는다.
- `SwaggerConfig` 설정 파일의 `@EnableWebMvc`어노테이션이 제거되었는가. 아직 존재한다면`CorsConfig`의 설정과 꼬여서 5173 이 다시 막힌다.

## 3. 디자인 토큰

### 3-1. 디자인 토큰 준비

PokeAPI 실습에서 만들었던 `montage.tokens.json` 을 그대로 가져온다. **React에 연결하고자 하는 대상 서버가 바뀌어도 이 파일은 바뀌지 않는다.** 다만 한 가지가 빠져 있다. **모서리(radius) 값이다.**

Montage 는 모서리를 `wds-theme` 에 토큰으로 두지 않고 각 컴포넌트의 `style.ts` 안에 적어 두었다. PokeAPI 실습에서 사용한 프롬프트가 `wds-theme` 만 읽으라고 시켰기 때문에 누락되었다. 따라서 카드와 버튼의 모서리를 토큰 없이 그리면 화면마다 값이 제각각이 된다.

```
design/montage.tokens.json 에 모서리(radius) 값이 빠져 있다.
montage-web-main/packages/wds/src/components 의 style.ts 들을 읽고
실제로 쓰인 모서리 값을 모아 이 파일에 더해줘.

- 기존 내용은 건드리지 않는다. radius 항목만 더한다.
- 같은 값이 여러 번 나오면 하나로 묶고, 어디에 쓰였는지 usage 에 적는다.

다 하면 모서리가 몇 종류인지 알려줘.
```

**확인**

- 색·타입 스타일 개수가 그대로인가. 줄었다면 기존 내용을 건드린 것이다
- 모서리가 **작은 값부터 완전한 원형(`9999px` 같은 것)까지** 범위를 덮는가

### 3-2. 디자인과 데이터의 분리

이 실습에서 연동할 서버는 바뀌었지만 아래 세 파일은 PokeAPI의 것을 그대로 쓴다.

```
design/montage.tokens.json   →   npm run tokens   →   src/tokens.css
                                 scripts/build-tokens.mjs
```

GitHub 이모지 API, PokeAPI, chap06, 그 외 어떤 서버와 연동하더라도 마찬가지로 **디자인(화면)은 디자인일 뿐, 데이터와 관련 없다.**

## 4. 에이전트 지침 파일 준비

### 4-1. 지침 파일 설계

`AGENTS.md` 를 **두 층으로 갈라 쓴다.**

| 층(layer)                     | 들어가는 절                                                 | 결정요소    |
| ----------------------------- | ----------------------------------------------------------- | ----------- |
| **1. 화면 디자인 규칙** | 사용 라이브러리 · 폴더 구조 · 상태 · 스타일 규칙 · 확인 | 디자인 토큰 |
| **2. 서버 통신 규칙**   | 서버 · 데이터 요청 · 응답 템플릿 · 명세가 빠뜨린 것      | API 명세    |

React와 연동할 서버가 다르다면 위층은 손대지 않고 **아래 층만 변경해주면 된다.** `CLAUDE.md` 에는 `@AGENTS.md` 한 줄만 적는다.

### 4-2. 화면 구현

4일차 지침에서 **그대로 가져오는 절들**이다. 한 가지만 고친다.

```
- 프로젝트는 npm create vite@latest <이름> -- --template react --eslint 로 만든다.
  --eslint 를 빼면 다른 린터가 깔린다.
```

`create-vite` 는 **린터를 고르라고 묻는다.** 명령에 답을 적어 두지 않으면 에이전트가 제 방식대로 만들고, 그 뒤 `npm run lint` 를 시키면 "린터가 없다"는 답이 돌아온다.

### 4-3. API 명세

**새로 쓰는 절들이다.** 명세(`api-docs.json`)를 읽고 아래 네 가지를 지침에 적는다.

**① 서버**

```
- 주소는 http://localhost:8080 이다. baseURL 은 api/ 의 axios 인스턴스 한 곳에만 적는다.
- 서버는 5173 만 허용한다. 5174 로 뜨면 요청이 막히므로 5173 으로 다시 띄운다.
```

**② 데이터 요청**

```
- 요청 주소는 menuCode · categoryCode 로 조립한다. 서버가 링크를 주지 않는다.
- 페이지 번호는 1부터 센다.
```

**③ 응답 템플릿**

정상 응답일 경우와 오류 응답일 경우의 템플릿 형태가 다르다.

```json
{ "httpStatus": 200, "message": "메뉴 목록 조회 성공", "result": { "menus": [] } }
```

```json
{ "code": "ERROR_CODE_00001", "description": "메뉴 조회 실패", "detail": "..." }
```

```
- result 안을 api/ 에서 꺼내 반환한다. 컴포넌트가 템플릿을 알지 않게 한다.
- 오류는 code 와 description 으로 판단한다. 오류 응답에는 httpStatus 가 없다.
- 삭제 응답의 httpStatus 는 204 지만 실제 HTTP 상태는 200 이다.
- orderableStatus 는 'Y' 또는 'N' 한 글자다.
```

**④ API 명세에 없는 내용**

명세를 뽑았다고 끝이 아니다. `api-docs.json` 을 열어 보면 세 군데가 비어 있다.

```
- CategoryDTO 스키마가 없다.
  필드는 categoryCode, categoryName, refCategoryCode, refCategoryName 이다.
- 최상위 카테고리(식사·음료·디저트)는 ref 두 값이 null 이다.
  메뉴는 하위 카테고리에 속한다.
- ErrorResponse 스키마가 없다. 위 오류 응답 템플릿을 따른다.
```

`result` 내부는 2-2 ③에서 description 에 적어 두었다면 메워진다. 앞의 둘은 **명세만으로는 알 수 없으므로** 지침으로 채워주면 된다.

## 5. 실습 — 메뉴 관리

### 5-1. 화면 디자인

아트보드 다섯 장을 만든다. 4일차의 세 장보다 늘어난 것은 **쓰기가 생겼기 때문**이다.

| 아트보드  | 담기는 것                                                      |
| --------- | -------------------------------------------------------------- |
| 레이아웃  | 헤더(로고·내비), 푸터                                         |
| 메뉴 목록 | 카드 그리드, 페이지네이션, 이름 검색, 가격 조건, 카테고리 필터 |
| 메뉴 상세 | 정보, 수정·삭제 버튼, 삭제 확인                               |
| 메뉴 폼   | 등록·수정 공용, 입력 검증                                     |
| 상태 모음 | 빈 상태, 오류, 로딩 스켈레톤                                  |

색과 간격은 토큰에서만 고른다. 토큰에 없는 값을 새로 만들지 않는다.

[claude.ai/artifact/8xygUDPVBbYorthRVmw8xo](https://claude.ai/artifact/8xygUDPVBbYorthRVmw8xo)

Claude 계정이 없으면 4일차와 같이 **정적 HTML 목업**으로 대신한다.

### 5-2. 개발 순서 정의

5-2-1. 레이아웃

화면을 담을 틀부터 만든다. API 를 한 번도 부르지 않고 **토큰이 실제로 먹는지** 먼저 확인하는 자리다.

```
헤더와 푸터가 있는 레이아웃을 만들어줘.
헤더에는 로고와 내비게이션(메뉴 목록, 메뉴 등록)을 둔다.

- 색과 글자 크기는 tokens.css 의 변수와 타입 스타일 클래스만 쓴다.
- 본문 자리는 비워 둔다.

API 는 아직 부르지 마.
```

**확인** — 브라우저에서 헤더·푸터가 토큰 색으로 보이는가.

#### 5-2-2. 전체 조회

검색도 페이징도 없이 목록이 뜨는 것까지만 만든다.

```
GET /api/menus 로 메뉴 목록을 카드 그리드에 띄워줘.

- 서버 요청은 src/api/ 안에만 둔다. 컴포넌트에서 axios 를 직접 부르지 않는다.
- 응답은 result 안을 꺼내 반환한다.

검색과 페이징은 아직 넣지 마.
카드에 무엇을 보여줄지 먼저 말하고 시작해줘.
```

**확인**

- 마지막 줄에 대한 답에 `menuName`·`menuPrice`·`categoryName` 이 나오는가.
  **PokeAPI 와 달리 추가 요청이 필요 없다.** DTO 가 완전하기 때문이다
- 네트워크 탭의 요청이 **한 번**인가

#### 5-2-3. 전체 조회 (feat. 페이징)

새 화면이 아니다. 앞 단계에 **페이징만 얹는다.**

```
GET /api/menus/pages 로 페이징을 붙여줘. 페이지 번호는 1부터다.
목록을 그리는 코드는 건드리지 않는다.
```

**확인**

- 변경된 파일 목록을 본다. 카드나 그리드가 바뀌었다면 순서가 틀어진 것이다
- `?page=1` 이 첫 페이지인가. 0부터 세면 빈 화면이 나온다

#### 5-2-4. 상세 조회

검색·필터·단일 조회를 함께 얹는다.

```
검색, 카테고리 필터, 상세 화면을 얹어줘.

- 검색어, 카테고리, 페이지는 컴포넌트 state 가 아니라 URL 쿼리스트링에 둔다.
- 카테고리 목록은 GET /api/categories 로 받고, 하위 카테고리만 고르게 한다.
- 가격 조건은 GET /api/menus/search 를 쓴다. 지정한 가격을 초과하는 것만 온다.
- 조건에 맞는 것이 없을 때의 빈 상태도 함께 만든다.
```

**확인**

- 주소창에 조건을 직접 넣고 새로고침 → 조건이 그대로 남는가
- 뒤로가기가 이전 조건으로 돌아가는가
- 가격 조건이 **초과**로 동작하는가. 미만으로 짐작했다면 명세를 안 읽은 것이다

#### 5-2-5. 등록 · 수정

**PokeAPI 에는 없던 단계다.** 여기서 처음으로 서버에 데이터를 보낸다.

```
메뉴 등록과 수정 화면을 만들어줘. 둘은 같은 화면을 쓴다.

- 등록은 POST /api/menus, 수정은 PUT /api/menus/{menuCode} 다.
- 등록할 때 menuCode 는 보내지 않는다. 서버가 채운다.
- orderableStatus 는 'Y' 또는 'N' 한 글자로 보낸다.
- 이름·가격·카테고리가 비어 있으면 보내지 않고 화면에 알린다.

저장이 끝나면 그 메뉴의 상세 화면으로 이동한다.
```

**확인**

- 등록 후 목록에 실제로 늘었는가
- 서버가 400 을 돌려줬을 때 화면에 **`description` 이 보이는가.**
  아무 메시지도 안 나오면 오류 템플릿을 안 읽은 것이다

#### 5-2-6. 삭제

```
상세 화면에 삭제를 붙여줘. DELETE /api/menus/{menuCode} 다.

- 바로 지우지 않는다. 한 번 더 확인을 받는다.
- 지운 뒤에는 목록으로 돌아간다.
```

**확인** — 삭제 응답의 실제 HTTP 상태는 **200** 이다. 204 로 짐작하고 분기했다면 걸린다.

### 5-3. (옵션) 제약 사항

- **이름 검색은 화면에서 거른다.** 서버에 이름 검색이 없다. 목록을 받아 두고 걸러야 한다
- **카테고리 필터도 마찬가지다.** `/api/categories` 는 목록만 주고, 카테고리별 메뉴 조회는 없다
- **메뉴 이름이 중복될 수 있다.** 표에 유일 제약이 없어서 같은 이름이 여러 건 보일 수 있다
- **정렬 API 를 쓰지 않았다.** `/api/menus/pages/sort` 가 있다. 여유가 있으면 붙여 본다
